Overview
--------

``style-checker`` is a Python project that checks whether type declarations in
Python source files follow a deliberately strict style.

Style Guide
-----------

The following rules govern declarations in module and function namespaces.
They concern variables bound through ordinary assignment syntax; names that
are exempt from these rules are described below. This style guide does not consider comments.
They can be anywhere without violating the style.

Required Variable Declarations
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Every variable assigned in a module's namespace must have a type annotation
that meets all of these requirements:

* It appears before the variable is used.
* It appears in the declaration block at the beginning of the scope.
* It does not assign a value (for example, ``count: int``, not ``count: int = 0``).
* It is listed in alphabetical order by variable name.
* It occurs exactly once.

A declaration is required whenever the variable is subject to these rules.
Conversely, a declaration for a variable that does not require one is an error.

Names Exempt from Declarations
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The declaration requirement does not apply to:

* Names automatically provided in a module's namespace.
* Names bound by nested ``class`` and ``def`` statements,
    i.e. of the classes and functions they define.
* Names bound by ``import`` statements.
* Temporary exception names introduced by ``except ... as ...``, which remain
    bound only for the duration of the exception handler.
* Each ``TypeVar`` and every similar construct is exempt from type annotation.

Declaration Placement
~~~~~~~~~~~~~~~~~~~~~

The annotations of a namespace may never be intermixed with other code,
but should form one continuous block.
This single block should be at the beginning of the module or function body.
Only the following may precede that block:

* A module or function docstring, if present. The docstring must be the first
    statement in its scope.
* ``import`` statements.
* A module's ``__all__`` definition, which follows the special rules below.


The ``__all__`` Variable
~~~~~~~~~~~~~~~~~~~~~~~~

The module-level ``__all__`` variable is exempt from the general declaration
rules and must instead satisfy all of the following requirements:

* Every module must define ``__all__``, even if it is an empty list.
* It must be annotated as ``list[str]``.
* It must be assigned a list literal containing string literals.
* Its elements must be in alphabetical order.
* Its definition must precede all imports except ``from __future__`` imports.
* It must be defined only once.

Function Scopes and Parameters
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The general declaration rules also apply to variables in every ``def`` and
``async def`` body. The special rules for ``__all__`` apply only at module level.

Every function parameter must have a type annotation, regardless of parameter kind.
This includes the first parameter (such as ``self`` or ``cls``), as well
as positional-only, keyword-only, ``*args``, and ``**kwargs`` parameters.
Function parameters do not need separate declarations in the function body.
The single keyword-only parameters should be alphabetically ordered.

Explicit Namespace Assignments
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

These rules do not restrict assignments performed explicitly through namespace
dictionaries or dictionary-like objects using string keys, such as
``globals()["name"] = value``.

Imports
~~~~~~~

The following ``import`` statements are forbidden:

* Wildcard imports (using ``*``)
* Importing annotations from ``typing`` that also exist in ``collections.abc``, e.g. ``Iterable``

Example
~~~~~~~

The following module illustrates the required order of statements and the
separation between declarations and assignments:

.. code-block:: python

    """An example module."""

    from __future__ import annotations

    __all__: list[str] = ["double"]

    count: int

    count = 2

    def double(value: int) -> int:
        result: int
        result = value * 2
        return result


Installation
------------

To install ``style-checker``, you can use ``pip``.
Open your terminal and run:

.. code-block:: shell

    pip install style-checker

Features
--------

Inherited features are only explained again
if there is further noteworthy information.

``style_checker.main(args: Iterable[str] | None = None, /) -> int``
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

This function is the CLI-rendering of ``run``.

``style_checker.run(*include: str, errfile: str = "-", errmsg: str = "{file}:{line}: {desc}", exclude: Iterable[str] = ()) -> int``
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``run`` checks Python source files and prints a diagnostic report.

``errfile`` is where this report is the file this report is printed to
(the default value ``"-"`` indicates ``sys.stderr``).

``include`` are the positional  arguments.
You may pass zero or more filenames or glob patterns,
e.g. ``**/*.py``.

``exclude`` is an iterable you can supply.
It excludes from the analysis files otherwise covered by ``include``.

``errmsg`` controls the format of **each diagnostic line**.
It defaults to ``"{file}:{line}: {desc}"``.
The supported substitution fields are:

- ``{file}``: the filename containing the violation;
- ``{line}``: the line number identifying the violation; and
- ``{desc}``: a description of the style rule or rules violated.

The specification requires **exactly one report line per offending ``def``
statement**, not one line for every individual defect in that function.
The checker also reports module-level violations (including invalid or missing
``__all__``), and multiple defects within a scope can be combined in the
``{desc}`` field.  An unreadable or syntactically invalid file likewise yields
a diagnostic.

``run`` returns ``0`` if no diagnostics were produced and ``1``
if at least one was produced.
