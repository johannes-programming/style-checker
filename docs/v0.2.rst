Overview
--------

``style-checker`` is a Python project that checks whether type declarations in
Python source files follow a deliberately strict style.

Style Guide
-----------

The following rules govern declarations in module and function namespaces.
The rules for ``Final`` annotations also apply in class namespaces.
They concern variables bound through ordinary assignment syntax; names that
are exempt from these rules are described below. Comments can be placed
anywhere, but the trailing-whitespace rule applies to them too.

Physical Line Whitespace, Indentation and Statement Placement (``LINE``)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``"LINE-STMT"``
^^^^^^^^^^^^^^^

Every decorator, compound-statement header and simple statement must start on
a physical line with only whitespace to its left. Python syntax already
enforces this for decorators and compound-statement headers. In particular,
multiple simple statements on one physical line and simple statements on the
same physical line as a compound-statement header are forbidden.

``"LINE-TW"``
^^^^^^^^^^^^^

No physical line may end with whitespace other than its line break. This also
applies to blank lines, comments, multiline strings and the final line of a
file without a line break.

``"LINE-IND"``
^^^^^^^^^^^^^^

Block indentation must consist of exactly four spaces per nesting level
(``"    "``). Tabs and other whitespace are not allowed for block indentation.
Blank lines, comment-only lines and continuation lines do not determine block
indentation.

``"LINE-DEEP"``
^^^^^^^^^^^^^^^

Each simple statement must start at no more than four indentation levels
deep, counted from the module level (level zero).

``"LINE-CONT"``
^^^^^^^^^^^^^^^

For each simple statement, compound-statement header and decorator separately,
no physical line used by it may start two or more indentation levels deeper
than its first physical line. The indentation width is inferred from the most
frequent indentation increase of an indented suite in the file (the smallest
increase wins a tie). Tabs are expanded to eight-column tab stops. If the file
has no indented suite, its indentation width cannot be inferred and only the
other rules are checked. Blank and comment-only lines are not used by a
statement, header or decorator unless they occur within a multiline string.
The body of a compound statement is not part of its header.

Annotations (``TYPE``)
~~~~~~~~~~~~~~~~~~~~~~

``"TYPE-MIS"``
^^^^^^^^^^^^^^

Every variable assigned in a module's namespace must have a type annotation,
subject to the exemptions described below. A declaration is required whenever
the variable is subject to these rules. A variable annotated with ``Final``
requires no separate declaration.

``"TYPE-BARE"``
^^^^^^^^^^^^^^^

A declaration must not assign a value (for example, ``count: int``, not
``count: int = 0``). An annotation with ``Final`` is not a declaration
and follows the separate rules below.

``"TYPE-SORT"``
^^^^^^^^^^^^^^^

Declarations must be listed in alphabetical order by variable name.

``"TYPE-ONCE"``
^^^^^^^^^^^^^^^

Each required declaration must occur exactly once.

``"TYPE-PROH"``
^^^^^^^^^^^^^^^

The declaration requirement does not apply to:

* Names bound by nested ``class`` and ``def`` statements,
    i.e. of the classes and functions they define.
* Names bound by ``import`` statements.

These names must not have separate declarations.

Temporary exception names introduced by ``except ... as ...``, which remain
bound only for the duration of the exception handler, must not have separate
declarations.

A declaration for a variable that does not require one is an error.
The declaration requirement does not apply to:

* Names automatically provided in a module's namespace.
* Each ``TypeVar`` and every similar construct, which is exempt from type
    annotation.

``"TYPE-TOP"``
^^^^^^^^^^^^^^

A declaration must appear before the variable is used and in the declaration
block at the beginning of the scope.

The declarations of a namespace should form one block at the beginning of the
module or function body. Within a function body, class definitions may be
intermixed with the declarations in that initial block.
Only the following may precede that block:

* A module or function docstring, if present. The docstring must be the first
    statement in its scope.
* ``import`` statements.
* A module's ``__all__`` definition, which follows the special rules below.

``"TYPE-FIN"``
^^^^^^^^^^^^^^

An annotation with ``Final`` or ``Final[T]`` is not a declaration. It must
not be included in the declaration block and need not be alphabetically
ordered. The earliest permitted position is immediately after the declaration
block (if any), but it may also appear later in the namespace.

The checker recognizes ``Final`` imported from ``typing`` or
``typing_extensions``, including qualified forms and import aliases in the
applicable or an enclosing module or function namespace. This is static
recognition of imports, not general type or name resolution.

A ``Final`` annotation must assign a value in the same statement, for
example, ``limit: Final[int] = 10`` or ``limit: Final = 10``.

A ``Final`` annotation must be a direct statement in its module, function,
async function or class body. It must not appear inside a suite that does not
introduce a separate namespace, such as an ``if``, ``for``, ``while``,
``try``, ``with`` or ``match`` suite (including their alternative suites).
A function or class defined inside such a suite introduces its own namespace.

For example:

.. code-block:: python

    __all__: list[str] = ["calculate"]

    from typing import Final

    def calculate(value: int) -> int:
        result: int
        scale: Final = 2
        offset: Final[int] = 1
        result = value * scale
        adjustment: Final = result + offset
        return adjustment

``"TYPE-ALL"``
^^^^^^^^^^^^^^

``__all__`` must be annotated as ``list[str]``.

``"TYPE-PARA"``
^^^^^^^^^^^^^^^

Every function parameter must have a type annotation, regardless of parameter kind.
This includes the first parameter (such as ``self`` or ``cls``), as well
as positional-only, keyword-only, ``*args``, and ``**kwargs`` parameters.
Function parameters do not need separate declarations in the function body.

``"TYPE-RET"``
^^^^^^^^^^^^^^

Every ``def`` and ``async def`` must have an explicit return type annotation,
including methods, constructors, nested functions, generators, and functions
with no return value (use ``-> None`` for the latter when appropriate).
Lambda expressions are exempt because Python does not support return
annotations on lambdas. The checker checks presence, not type correctness.
A missing annotation is reported on the physical line of the signature's
closing colon.

``"TYPE-UPDT"``
^^^^^^^^^^^^^^^

Annotations must not use legacy aliases from ``typing`` for which Python 3.11
provides modern alternatives. This applies to variable, parameter and return
annotations, including class attributes, nested types and quoted forward
annotations. The checker recognizes direct imports, qualified references and
import aliases in the relevant namespace. Importing the names alone, using
those names in runtime expressions outside annotations, and using typing-only
constructs without a modern Python 3.11 replacement are not violations.
Recognition is static, not general runtime name or type resolution; it does
not follow re-exports, dynamic aliases or type alias assignments. Type comments
are not annotations for this rule.

The forbidden names and their alternatives are:

* Builtins: ``List`` → ``list``, ``Dict`` → ``dict``, ``Set`` → ``set``,
    ``FrozenSet`` → ``frozenset``, ``Tuple`` → ``tuple``, ``Type`` → ``type``,
    and ``Text`` → ``str``.
* ``collections``: ``ChainMap``, ``Counter``, ``OrderedDict`` (same names),
    ``DefaultDict`` → ``defaultdict``, and ``Deque`` → ``deque``.
* ``collections.abc``: ``AbstractSet`` → ``Set``, and the following names
    unchanged: ``AsyncGenerator``, ``AsyncIterable``, ``AsyncIterator``,
    ``Awaitable``, ``ByteString``, ``Callable``, ``Collection``, ``Container``,
    ``Coroutine``, ``Generator``, ``Hashable``, ``ItemsView``, ``Iterable``,
    ``Iterator``, ``KeysView``, ``Mapping``, ``MappingView``, ``MutableMapping``,
    ``MutableSequence``, ``MutableSet``, ``Reversible``, ``Sequence``, ``Sized``,
    and ``ValuesView``.
* ``contextlib``: ``ContextManager`` → ``AbstractContextManager`` and
    ``AsyncContextManager`` → ``AbstractAsyncContextManager``.
* ``re``: ``Match`` and ``Pattern`` (same names).
* Unions: ``Optional[T]`` → ``T | None`` and ``Union[T, U]`` → ``T | U``.

For example, ``typing.List[typing.Optional[int]]`` must instead be written
as ``list[int | None]``. The diagnostic lists the original typing names on
the physical line of their use (the string's starting line for quoted types).

``"TYPE-NONE"``
^^^^^^^^^^^^^^^

If a union in an annotation is written with ``|`` and contains ``None``,
``None`` must be the last member of that union. Parentheses do not change
member order: ``(int | None) | str`` and ``None | (int | str)`` are forbidden;
``int | str | None`` is allowed. Distinct nested unions are checked separately,
so ``list[int | None] | str`` is allowed. An annotation consisting of ``None``
alone is also allowed. The offending ``None`` is reported on its physical line
(or the starting line of its quoted annotation). Runtime bitwise-or operations,
``Literal`` values and ``Annotated`` metadata are not union annotations.

The ``__all__`` Variable (``ALL``)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The module-level ``__all__`` variable is exempt from the general declaration
rules and must satisfy ``TYPE-ALL`` above and the following requirements.

``"ALL-MIS"``
^^^^^^^^^^^^^

Every module must define ``__all__``, even if it is an empty list.

``"ALL-LIST"``
^^^^^^^^^^^^^^

``__all__`` must be assigned a list literal.

``"ALL-STR"``
^^^^^^^^^^^^^

The elements of ``__all__`` must be string literals.

``"ALL-ORD"``
^^^^^^^^^^^^^

The elements of ``__all__`` must be in alphabetical order.

``"ALL-IMP"``
^^^^^^^^^^^^^

The definition of ``__all__`` must precede all imports except
``from __future__`` imports.

``"ALL-DUP"``
^^^^^^^^^^^^^

``__all__`` must be defined only once.

``"ALL-DEAD"``
^^^^^^^^^^^^^^

Every unused module-level name must be listed in the module's literal
``__all__`` list. This applies to imported names, assigned variables, functions
and classes bound in module scope, including module-level control-flow blocks.
A name missing from ``__all__`` is reported if it is not read elsewhere within
that module. Names referenced inside nested functions and classes count as used;
references to a shadowing local variable do not. Uses solely in postponed
annotations also count. Python's predefined module names and ``__all__`` are
exempt. The diagnostic is reported at the end of the module.

This is static name analysis, not an inspection of other modules or dynamic
lookups (such as ``globals()[name]``). It intentionally treats ``__all__`` as
the sole declaration of a public export, even though Python permits importing
other names explicitly.

Function Scopes and Parameters (``DEF``)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The general declaration rules also apply to variables in every ``def`` and
``async def`` body. The special rules for ``__all__`` apply only at module level.

``"DEF-RPLC"``
^^^^^^^^^^^^^^

A function parameter must never be reassigned. This applies to all parameter
kinds, including parameters of lambda expressions. Assignment to the parameter
name is forbidden, including augmented assignment, assignment expressions,
and rebinding through a loop target, context manager, pattern capture, exception
handler, import, or definition. Reassignment through ``nonlocal`` is also
forbidden. A binding of the same name in a different namespace is not a
reassignment of the parameter. Deleting the name without assigning a new value
is not reassignment under this rule.

The object referenced by a parameter may be mutated. For example:

.. code-block:: python

    def update(items: list[int]) -> None:
        items.append(1)
        items[0] = 2

    def replace(items: list[int]) -> None:
        items = [1]  # DEF-RPLC
        items += [2]  # DEF-RPLC, even if the operation mutates the list

``"DEF-SORT"``
^^^^^^^^^^^^^^

The single keyword-only parameters should be alphabetically ordered.

``"DEF-SELF"``
^^^^^^^^^^^^^^

An undecorated ``def`` or ``async def`` statement must have a positional-only
first parameter if its nearest enclosing ``class``, ``def`` or ``async def``
statement is a ``class`` statement. Intervening control-flow statements do not
change this rule. A ``def`` or ``async def`` statement whose innermost decorator
is ``@classmethod`` must also have a positional-only first parameter, regardless
of its enclosing statements. In both cases, a first parameter is required.

For example:

.. code-block:: python

    __all__: list[str] = ["Example"]

    class Example:
        def method(self: "Example", /, value: int) -> int:
            return value

        @classmethod
        def build(cls: type["Example"], /) -> "Example":
            return cls()

        @staticmethod
        def static(value: int) -> int:
            return value

Omitting the ``/`` in ``method`` or ``build`` would violate the rule.

Symbols (``SYM``)
~~~~~~~~~~~~~~~~~

``"SYM-WILD"``
^^^^^^^^^^^^^^

Wildcard imports (using ``*``) are forbidden.

``"SYM-SEMI"``
^^^^^^^^^^^^^^

Semicolons are forbidden as Python syntax, including trailing semicolons and
semicolons separating statements on the same or different physical lines.
Semicolons inside comments or string literals are not syntax and are permitted.
Each physical line containing a semicolon token produces one diagnostic.
This rule is independent of ``LINE-STMT``.

Syntax Errors (``SYN``)
~~~~~~~~~~~~~~~~~~~~~~~

Syntax errors and their subclasses use their full exception class name as
the personal name: ``SYN-SyntaxError``, ``SYN-IndentationError``, and
``SYN-TabError``. The checker stops checking the file at the syntax-error
line, even if that diagnostic is ignored.

Example
~~~~~~~

The following module illustrates the required order of statements and the
separation between declarations and assignments:

.. code-block:: python

    """An example module."""

    from __future__ import annotations

    __all__: list[str] = ["count", "double"]

    count: int

    count = 2

    def double(value: int) -> int:
        result: int
        result = value * 2
        return result


Installation
------------

To install ``style-checker``, you can use ``pip``.
Open your terminal and run:

.. code-block:: shell

    pip install style-checker

------

Features
--------

Inherited features are only explained again
if there is further noteworthy information.

``style_checker.main(args: Iterable[str] | None = None) -> int``
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

This function is the CLI-rendering of ``run``.

``style_checker.parse_args(args: Iterable[str] | None = None) -> Namespace``
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``style_checker.run(*include: str, exclude: Iterable[str] = (), ignore: Iterable[str] = (), outfile: str = "-", outmsg: str = "{file}:{line}:{rule}: {desc}!\n") -> None``
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``run`` checks Python source files and prints a diagnostic report.

``outfile`` is where this report is the file this report is printed to
(the default value ``"-"`` indicates ``sys.stdout``).

``include`` are the positional  arguments.
You may pass zero or more filenames or glob patterns,
e.g. ``**/*.py``.

``exclude`` is an iterable you can supply.
It excludes from the analysis files otherwise covered by ``include``.

``ignore`` is an iterable of case-sensitive rule marks or family names.
Style rule marks consist of a family and personal name, each containing two
to four uppercase ASCII letters, separated by a dash. Syntax-error marks
use the full exception class name after ``SYN-`` instead.
Ignored issues are omitted from the report. A family name suppresses all
rules in that family; an empty string suppresses every diagnostic, including
syntax errors. Unknown marks have no effect. With no ignore arguments, all
findings are reported. On the command line, repeat ``--ignore=MARK`` to
combine filters, for example::

    python -m style_checker --ignore=LINE-TW --ignore=TYPE-MIS example.py
    python -m style_checker --ignore=TYPE example.py
    python -m style_checker --ignore=LINE --ignore=SYN example.py
    python -m style_checker --ignore=SYN-IndentationError example.py
    python -m style_checker --ignore= example.py

The corresponding API call for suppressing all diagnostics is
``run("example.py", ignore=[""])``. An empty iterable (the default) does not
suppress anything. Files are still checked, and file-reading errors are not
suppressed.

``outmsg`` controls the format of **each diagnostic message**.
It defaults to ``"{file}:{line}:{rule}: {desc}!\n"``.
The supported substitution fields are:

- ``{file}``: the filename containing the violation;
- ``{line}``: the line number identifying the violation;
- ``{rule}``: the case-sensitive rule mark; and
- ``{desc}``: the rule description, including any relevant details, without
    an appended exclamation mark. It does not include the rule mark.

Every style-rule description uses the word ``should``. Syntax-error
descriptions instead retain the original Python exception message.

The default format supplies both the final exclamation mark and newline.
Custom formats can omit, replace or move either of them. No separator is
added automatically. For example::

    run("example.py", outmsg="{rule}\n\n")
    run("example.py", outmsg="{rule}; ")
    run("example.py", outmsg="{rule}")

The same applies to ``--outmsg`` on the command line: pass an actual newline
if needed (for example, in Bash, ``--outmsg=$'{rule}\n'``). A literal
backslash followed by ``n`` is not converted into a newline by the checker.
Each exception in the raised ``ExceptionGroup`` contains the formatted
message, including any separator supplied by ``outmsg``.

The checker produces **exactly one report message per distinct combination of
file, physical line, and rule**. Repeated findings for the same combination
are consolidated, with distinct affected names listed in alphabetical order.
The report is ordered by ``os.path.abspath(file)``, then by numeric line
number, then by rule mark in alphabetical order. File paths retain their
original spelling in the output; absolute paths are used for ordering and
identifying duplicate file arguments. These guarantees also apply to custom
``outmsg`` formats, even when a format omits the distinguishing fields.
The physical-line rules include ``LINE-NL`` (a nonempty file must end
with a linebreak) and ``LINE-BL`` (no whitespace-only physical lines at
end of file). ``LINE-NL`` is reported on the last physical line, and
``LINE-BL`` is reported once per trailing whitespace-only line, including
empty lines. LF, CRLF and CR linebreaks are accepted. An empty file is
exempt from both rules. Whitespace-only lines elsewhere are unaffected by
``LINE-BL``; the existing ``LINE-TW`` rule still applies independently.

The checker also reports module-level violations (including invalid or missing
``__all__``) and syntax errors. For a syntax error, ``{rule}`` is
``"SYN-" + type(err).__name__`` (for example, ``SYN-SyntaxError``,
``SYN-IndentationError`` or ``SYN-TabError``), and ``{desc}`` is ``err.msg``.
Only style issues on physical lines strictly before the reported syntax-error line can be
reported for that file, even when the syntax error itself is ignored.
Ignoring a full syntax rule mark matches that exact class, not its
subclasses. Ignoring ``SYN`` matches the entire family. File-reading failures are propagated as exceptions.

If any non-ignored diagnostics were produced then ``run`` raises an
``ExceptionGroup``.
